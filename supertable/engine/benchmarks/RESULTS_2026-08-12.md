# IslandDB baseline — 2026-08-12

This baseline compares the production `DUCKDB` and `ISLANDDB` executor
paths. DuckDB is the correctness oracle. Every workload passed exact parity
for column order, pandas dtypes, values, and row order **before** timing.

The corpus is deterministic, ZSTD-compressed, wide Parquet. The table includes
two query columns plus eight high-entropy payload columns. Each number below is
the median of three warm samples; the first fresh-process sample is retained in
the raw JSON artifacts. OS page cache was uncontrolled, so these are warm local
scan/operator results—not claims about cold object-store network performance.

A separate final KB smoke after semantic hardening (the same corpus and three
warm samples) measured IslandDB at 0.912× point, 0.956× 1%-range, and 1.099×
projection relative to DuckDB. Exact parity still passed. This variance at the
tiny tier reinforces that sub-megabyte differences are planning noise, not a
routing signal; the larger-tier trends below are the useful result.

Test host: Linux 6.8, 8 allocated CPUs on a 12th-generation Intel Core
i7-12700H, 15 GiB RAM, Python 3.10.12, DuckDB 1.5.4, Polars 1.42.1,
PyArrow 18.1.0, and pandas 2.2.3.

Interpretation:

- IslandDB's strongest first-phase result is a wide projection scan: it reads
  one compressed metric column and becomes increasingly faster as physical
  source size grows.
- Point and narrow-range queries are dominated by planning/connection overhead
  after file and row-group pruning; the two engines are therefore closer.
- The 67 MB 1% range is the one measured regression (about 2%). This is why
  IslandDB remains explicit-only and the AUTO router is disabled by default.
- A cold remote miss can still favor DuckDB: IslandDB's shared cache stores a
  complete immutable Parquet object, whereas DuckDB can issue remote range
  requests for just footer and selected chunks. Cold and warm remote workloads
  must be benchmarked against the deployment's real object store before AUTO
  is enabled.

Reproduce with:

```bash
python -m supertable.engine.benchmarks \
  --sizes kb,mb,1gib,10gib --allow-large \
  --workloads point,range_1pct,projection --repeats 3
```
