# 10 GiB, five-of-thirty-column, one-percent range comparison

## Outcome

IslandDB now wins this selective workload in both process-cold and warm
execution. The production benchmark used explicit engines in separate worker
processes, the engines' normal CPU policies (no hidden DuckDB thread pin), and
seven warm samples. DuckDB was the blocking result oracle before timing.

| Metric | DuckDB | IslandDB | IslandDB difference |
|---|---:|---:|---:|
| Process-cold wall | 275.33 ms | **125.23 ms** | **54.5% lower** |
| Warm wall median | 107.36 ms | **55.29 ms** | **48.5% lower / 1.94x speed** |
| Warm wall range | 95.18–132.54 ms | **49.46–66.46 ms** | lower and tighter |
| Process-cold CPU | 726.32 ms | **212.31 ms** | **70.8% lower** |
| Warm CPU median | 241.62 ms | **81.08 ms** | **66.4% lower** |
| Process-cold RSS delta | **35.77 MiB** | 52.82 MiB | IslandDB 47.7% higher |
| Warm RSS-delta median | **1.75 MiB** | 9.48 MiB | IslandDB 5.42x higher |
| Maximum process RSS | **219.00 MiB** | 252.18 MiB | IslandDB 15.2% higher |
| Spill | 0 | 0 | equal |
| Exact result | DuckDB oracle | exact match | digest `77d74069…371fde` |

The exact result was `metric_sum=32,068,048,917`, `max_dimension=1023`, and
both payload counts were `64,136`.

## Exact workload

- Deterministic local ZSTD Parquet: 10,737,429,031 physical bytes,
  6,413,677 rows, 81 files, 30 public columns.
- Query reads `id`, `metric`, `dimension`, `payload_00`, and `payload_01` and
  applies one contiguous one-percent `id` range.
- Sealed file statistics prune 81 files to 2, leaving 268,433,931 candidate
  physical bytes.
- Row-group statistics retain 16 of 38 candidate groups.
- Exact compressed selected chunks are 9,055,635 bytes (8.64 MiB); the exact
  decoded estimate is 72,445,080 bytes (69.09 MiB).
- DuckDB used its production-derived 20-thread setting on this 8-logical-CPU,
  1-GiB-memory-limit configuration. Polars used its 8-thread process pool.

## Before versus final IslandDB

The original checked result for this same corpus/query was 287.38 ms cold and
162.88 ms warm median. The final process-cold run is therefore 56.4% faster and
the final warm median is 66.1% faster. The original/final runners used different
warm repeat counts, so those percentages describe the measured campaign rather
than a microbenchmark confidence interval.

The last scheduling experiment selected Polars' column-parallel scanner only
for sealed complete local scans of at most 32 MiB that require four to eight
physical columns. Four paired fresh-process experiments measured about 13.5%
lower warm wall time and 9.2% lower warm RSS for that narrow gate. `low_memory`
slowed the query by about 41% without reducing RSS; serial scanning reduced RSS
but exceeded the accepted 5% slowdown. Wide, incomplete, larger, and remote
scans retain Polars' adaptive strategy.

## I/O interpretation

The primary process-cold series does not evict the kernel page cache. Its
reported physical reads (DuckDB 20 KiB and IslandDB 0) are therefore not a
cold-storage comparison. In a separate best-effort `posix_fadvise` run,
IslandDB reported 9,396,224 process read bytes—close to the 9,055,635-byte
compressed scan estimate—but DuckDB exposes only its internal profiler's
20-KiB metadata counter, not comparable process physical I/O. No cross-engine
disk-byte conclusion is drawn from those incompatible counters.

On remote immutable objects, IslandDB's version-sealed range reader persists
the exact footer and compressed ranges demanded by Arrow. Its range telemetry
separately reports logical requests, cache hits, remote requests/bytes,
checksum validations/skips, repairs, and evictions.

## Reproduce

```bash
env -u SUPERTABLE_DUCKDB_THREADS \
python -m supertable.engine.benchmarks \
  --sizes 10gib --allow-large \
  --workloads range_1pct_5cols --repeats 7 \
  --payload-columns 26 \
  --corpus-root /tmp/island-telemetry-corpus \
  --cache-root /tmp/island-audit-final-postaudit-cache \
  --home-root /tmp/island-audit-final-postaudit-home \
  --output /tmp/island-audit-final-postaudit-process.json
```

`cold` means a fresh worker, connection, and application cache. Use
`--cold-mode fadvise` for a separately labelled best-effort page-cache eviction
run; the kernel does not guarantee eviction.
